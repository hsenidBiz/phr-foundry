# HRM-DB Deployment Script

Treat this package as the portable source of truth; do not assume repository-local guidance exists. Read `references/strict-sql-rules.md` before generating or reviewing SQL.

## Intake

1. Require the complete source SQL for creation or conversion. Do not generate business SQL from a prose-only requirement. For review-only work, require the SQL or files to review.
2. Collect the user name, feature ID, task ID, module/folder, and type (`CR`, `CRB`, `RM`, or `QRB`). Infer creation/conversion from the request; use review-only mode only when explicitly requested.
3. If the SQL inserts into or updates `HS_FORM_LABEL_MAP`, ask whether other languages are required. If yes, collect the required languages or regions. Do not ask for culture codes at intake.
4. Ask once for all missing information. If the reply remains incomplete, ask only for the remaining items.
5. Once all required information is available, proceed directly. Do not present an Input summary, Proposed changes summary, or confirmation gate.

Never offer or perform query enhancement, optimization, normalization, cleanup, or reformatting. If a mandatory safety rule cannot be satisfied without changing supplied SQL, stop and request corrected source SQL.

## Preserve supplied SQL

Treat supplied SQL as an immutable source block.

- Copy every supplied statement into the root deployment script without changing whitespace, comments, columns, column order, values, predicates, aliases, batches, or business logic.
- Add only agent-owned rerunnability guards, traceability banners, required `GO` separators outside the source block, deployment registration, and other mandatory deployment scaffolding.
- Keep agent-generated validation queries out of root and localization SQL files. Report them only in the final response or PR review notes unless the user explicitly supplied the `SELECT` as source SQL.
- Apply strict SQL patterns only to conditions or scaffolding generated by the agent. Never use a reference example as a replacement template for the user's statement.
- Preserve a user-supplied guard. If that guard is unsafe or noncompliant, stop and ask the user to supply corrected SQL; do not rewrite it.
- Before completion, compare the source SQL with the copied root-script statements line by line and compare each `INSERT` column/value count. Any unintended difference is a blocker.

## Inspect and create

After intake is complete:

1. Read `references/deployment-rules.md` and `references/reviewer-checklist.md`.
2. Inspect numeric root SQL files in `src/PeoplesHR/Current/<MODULE>/`. Ignore nested localization files and malformed names. Use the next index while preserving the module's observed zero-padding and suffix style.
3. Inspect `src/PeoplesHR/Current/dep.xml`; create one exact registration immediately before the first Version record.
4. Apply the matching generated guard around the unchanged source SQL. Stop for ambiguous business keys, destructive intent, unsafe broad data changes, missing ER groups/descriptions, dependencies, or other decisions that cannot be resolved from repository evidence.
5. Create the root SQL file, required localization changes, and the `dep.xml` entry without another confirmation.
6. Validate with repository search, file inspection, XML inspection, and diff tools. Check filename/index, banners, guards, unchanged source SQL, localization shape, and exact unique `dep.xml` placement. Prepare validation queries for the final response only; do not append them to deployment files.

## Column descriptions

- Generate one complete, self-contained `MS_Description` add-or-update block for each column.
- Keep the table-level description in its own block, then emit each column-level block separately with a literal column name and description.
- Never collect descriptions in a temporary table, table variable, `VALUES` dataset, or other staging structure. Never iterate descriptions with a cursor, `WHILE` loop, dynamic SQL, or any shared batch mechanism.
- Repeat the explicit `IF EXISTS` / `sp_updateextendedproperty` / `ELSE` / `sp_addextendedproperty` pattern for every column because the diagram framework requires individually defined descriptions.

## Localization

For each confirmed language or region:

1. Inspect `Localizations/<Region>/data.sql` and `scripts.sql` in the target module first, then matching folders in other current modules.
2. Extract culture evidence only from `HS_FORM_LABEL_MAP` statements. Reuse one unambiguous established culture and report its source paths. Ask the user only when no culture is found or evidence conflicts.
3. Generate the localized statement from the supplied English statement. Preserve its statement shape, column list, column order, value count, predicates, and every nonlocalized value. Change only the culture and the automatically translated label value.
4. Apply the strict generated label guard using exactly `FLM_LABEL_KEY`, `FLM_LABEL_CULTURE`, and `FLM_LABEL_TYPE`.
5. Write only the guarded localized data statement and traceability banners. Do not append a validation `SELECT`, diagnostic query, or result-preview query unless it was part of the user's supplied SQL.

Use the sections in `references/output-contract.md` for the final result.
